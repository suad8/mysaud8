# خطة بناء متجر إلكتروني + لوحة تحكم

> **المشروع:** متجر إلكتروني مستقل (من الصفر) مع لوحة تحكم إدارية خاصة
> **السوق المستهدف:** السعودية — عربي/RTL افتراضياً، الريال السعودي، ضريبة القيمة المضافة 15%
> **آخر تحديث:** 2026-09-20

---

## 1. نظرة عامة

نبني منصة تجارة إلكترونية كاملة في مستودع واحد (Monorepo بسيط عبر Next.js App Router)، تتكوّن من ثلاث طبقات:

| الطبقة | الوصف | المسار |
|---|---|---|
| **واجهة المتجر** (Storefront) | ما يراه العميل: تصفح، بحث، سلة، دفع، حساب | `src/app/(storefront)` |
| **لوحة التحكم** (Admin) | ما يراه صاحب المتجر: منتجات، طلبات، عملاء، تقارير، إعدادات | `src/app/(admin)/admin` |
| **واجهة برمجية** (API) | نقاط نهاية REST للسلة، الدفع، Webhooks | `src/app/api` |

الثلاثة تشترك في نفس قاعدة البيانات ونفس طبقة منطق الأعمال (`src/server`)، ما يلغي الحاجة لمزامنة بين خدمتين منفصلتين في هذه المرحلة.

### لماذا هذا الاختيار؟

- **Next.js 15 (App Router)** — عرض من الخادم (SSR) يعني صفحات منتجات سريعة ومؤرشفة في محركات البحث، وهو أهم عامل نمو لمتجر جديد.
- **React Server Components** — استعلامات قاعدة البيانات تُنفّذ على الخادم مباشرة بدون طبقة API وسيطة لكل شاشة.
- **Prisma + PostgreSQL** — مخطط بيانات مُعرَّف بوضوح مع ترحيلات (migrations) قابلة للمراجعة، وأمان أنواع كامل من قاعدة البيانات حتى الواجهة.
- **مستودع واحد** — المتجر ولوحة التحكم ينشران معاً، ولا تتفكك الأنواع بينهما.

## 2. البنية التقنية

### 2.1 الحزمة التقنية

| المجال | الاختيار | السبب |
|---|---|---|
| إطار العمل | Next.js 15 (App Router) | SSR + RSC + Server Actions |
| اللغة | TypeScript (strict) | أمان أنواع شامل |
| التنسيق | Tailwind CSS v4 | سريع، ودعم RTL عبر الخصائص المنطقية |
| قاعدة البيانات | PostgreSQL 16 | معاملات ACID، دقة مالية عبر `Decimal` |
| ORM | Prisma 6 | ترحيلات، أنواع مولّدة، استعلامات آمنة |
| الجلسات | جلسات على الخادم (HttpOnly cookie) | لا حاجة لمزوّد خارجي |
| التحقق | Zod | تحقق موحّد من المدخلات في الخادم والعميل |
| الصور | Next/Image + مخزن S3-compatible | تحسين تلقائي وتقديم WebP |
| الرسوم البيانية | Recharts | تقارير لوحة التحكم |
| الاختبارات | Vitest + Playwright | وحدات + مسار شراء كامل |

### 2.3 قاعدة القرار المعمارية

**كل تعديل على البيانات يمر عبر `src/server/**` فقط.** المكونات لا تستدعي Prisma مباشرة ولا تحسب أسعاراً. السبب: السعر النهائي والضريبة والخصم يجب أن تُحسب في مكان واحد، وإلا اختلفت السلة عن الفاتورة.

## 3. نموذج البيانات

### 3.1 الكيانات الأساسية

```
Product ──< ProductVariant ──< InventoryItem
   │              │
   │              └──< OrderItem >── Order ──< Payment
   │                                   │
   ├──< ProductImage                   ├──< OrderEvent   (سجل تغيّر الحالة)
   │                                   └──< Shipment
   └──> Category (شجرة) / Brand

Customer ──< Address
   │
   ├──< Order
   ├──< Cart ──< CartItem
   └──< Review

AdminUser ──> Role ──< Permission
Coupon / Discount ──> قواعد التطبيق
```

### 3.2 قرارات مهمة في المخطط

| القرار | التفصيل |
|---|---|
| **الأسعار بـ `Decimal(12,2)`** | لا `Float` أبداً — الأخطاء العشرية تتراكم في الفواتير |
| **المتغيّرات (Variants)** | كل منتج له متغيّر واحد على الأقل. المقاس/اللون يُخزَّن كـ `options` JSON + `sku` فريد |
| **لقطة السعر في الطلب** | `OrderItem` يخزّن السعر والاسم وقت الشراء — تغيير سعر المنتج لاحقاً لا يغيّر الفواتير القديمة |
| **المخزون بحجز** | `InventoryItem` فيه `onHand` و `reserved`. المتاح = `onHand - reserved`. الحجز يتم عند بدء الدفع ويُحرَّر عند الفشل أو انتهاء المهلة |
| **حالات الطلب** | `PENDING → PAID → PROCESSING → SHIPPED → DELIVERED` + `CANCELLED / REFUNDED`. كل انتقال يُسجَّل في `OrderEvent` |
| **الحذف الناعم** | `deletedAt` على المنتجات — لأن الطلبات القديمة تشير إليها |
| **الترجمة** | حقول `nameAr/nameEn` مباشرة بدل جدول ترجمة منفصل (أبسط للغتين) |

### 3.3 الضريبة والأسعار

- الأسعار المعروضة **شاملة الضريبة** (المعيار في السعودية).
- `Order` يخزّن: `subtotal`، `discountTotal`، `shippingTotal`، `taxTotal`، `grandTotal` — كلها محسوبة ومحفوظة، لا تُعاد حسابتها عند العرض.
- نسبة الضريبة في الإعدادات لا في الكود (قابلة للتغيير).

## 4. الوحدات الوظيفية

### 4.1 واجهة المتجر

| الوحدة | المحتوى |
|---|---|
| **الرئيسية** | بانر رئيسي، تصنيفات، منتجات مميزة، الأكثر مبيعاً، شريط ثقة (شحن/إرجاع/دفع) |
| **التصفح** | شبكة منتجات + فلاتر (تصنيف، سعر، ماركة، توفر) + ترتيب + ترقيم |
| **صفحة المنتج** | معرض صور، اختيار متغيّر، السعر وحالة التوفر، الوصف، التقييمات، منتجات مشابهة |
| **البحث** | بحث نصي بالعربي مع تطبيع الهمزات/التاء المربوطة |
| **السلة** | درج جانبي + صفحة كاملة، تعديل الكمية، كوبون، ملخص الطلب |
| **الدفع** | خطوة واحدة: عنوان → شحن → دفع. دعم الشراء كضيف |
| **الحساب** | الطلبات، تتبع الشحنة، العناوين، المفضلة |

### 4.2 لوحة التحكم

| الوحدة | المحتوى |
|---|---|
| **الرئيسية** | مبيعات اليوم/الأسبوع/الشهر، عدد الطلبات، متوسط قيمة الطلب، رسم بياني، أحدث الطلبات، تنبيه مخزون منخفض |
| **المنتجات** | جدول + بحث/فلترة، إضافة/تعديل مع متغيّرات وصور، تفعيل/أرشفة، استيراد وتصدير CSV |
| **الطلبات** | جدول بحالات، تفاصيل الطلب، تغيير الحالة، طباعة فاتورة، استرجاع، ملاحظات داخلية |
| **العملاء** | قائمة، ملف العميل (طلباته، إجمالي إنفاقه، عناوينه) |
| **المخزون** | كميات لكل SKU، تعديل سريع، سجل الحركة |
| **الخصومات** | كوبونات (نسبة/مبلغ/شحن مجاني)، حد أدنى، تاريخ صلاحية، حد استخدام |
| **التقارير** | مبيعات بالفترة، أفضل المنتجات، حسب التصنيف، السلات المتروكة، معدل التحويل |
| **الإعدادات** | بيانات المتجر، الشعار والألوان، الشحن والمناطق، بوابات الدفع، الضريبة، المستخدمون والصلاحيات |

### 4.3 الصلاحيات

ثلاثة أدوار جاهزة: `OWNER` (كل شيء) · `MANAGER` (كل شيء عدا الإعدادات الحساسة والمستخدمين) · `STAFF` (طلبات ومخزون فقط). الصلاحيات تُفحص في طبقة `src/server/auth` لا في المكونات.

## 5. التكاملات

### 5.1 الدفع

| البوابة | التغطية | الأولوية |
|---|---|---|
| **Moyasar** | مدى، فيزا/ماستر، Apple Pay، STC Pay | المرحلة 3 — البوابة الأساسية |
| **Tabby** | تقسيط على 4 دفعات | المرحلة 4 |
| **Tamara** | ادفع لاحقاً | المرحلة 4 (اختياري) |
| الدفع عند الاستلام | — | المرحلة 3 (مدمج، بدون تكامل) |

**التصميم:** واجهة `PaymentProvider` موحّدة (`createPayment` / `verifyPayment` / `refund`) وكل بوابة تنفّذها. إضافة بوابة جديدة = ملف واحد، بدون لمس منطق الطلبات.

**الأمان:** الطلب لا يُعتبر مدفوعاً إلا بعد **تأكيد من Webhook موقّع** من البوابة — لا يُعتمد على عودة المتصفح أبداً. كل Webhook يُتحقق من توقيعه ويُعالج بمفتاح idempotency لمنع التكرار.

### 5.2 الشحن

- حساب تكلفة الشحن بالمنطقة والوزن (جدول `ShippingZone` + `ShippingRate`).
- شحن مجاني فوق مبلغ معيّن (قابل للضبط).
- تكامل أرامكس/سمسا في المرحلة 5 (إنشاء بوليصة + تتبع).

### 5.3 تكاملات أخرى

- **الفواتير:** فاتورة ضريبية مبسّطة PDF مع رمز QR بصيغة ZATCA TLV — المرحلة 5.
- **الرسائل:** بريد معاملاتي (تأكيد طلب، شحن) + واتساب/SMS للتحديثات.
- **التحليلات:** أحداث GA4 / Meta Pixel عبر طبقة `analytics` واحدة.

## 6. الأمان

| الجانب | الإجراء |
|---|---|
| كلمات المرور | Argon2id، لا تُسجَّل أبداً |
| الجلسات | كوكيز `HttpOnly` + `SameSite=Lax` + `Secure` |
| CSRF | Server Actions محميّة أصلاً؛ نقاط API تتحقق من `Origin` |
| المدخلات | تحقق Zod في الخادم — مدخلات العميل غير موثوقة دائماً |
| حقن SQL | Prisma بمعاملات مُعدّة، لا SQL خام إلا عند الضرورة وبمعاملات |
| الحد من المعدل | على تسجيل الدخول، الكوبونات، وبدء الدفع |
| الأسرار | متغيّرات بيئة فقط، ولا مفاتيح في كود العميل |
| الدفع | لا نخزّن بيانات بطاقات إطلاقاً — تُرسل للبوابة مباشرة (PCI SAQ-A) |
| الرفع | فحص نوع الملف وحجمه، تخزين خارج جذر الموقع |
| السجلات | تسجيل كل عملية إدارية حساسة في `AuditLog` |

## 8. التشغيل والنشر

### التطوير المحلي

```bash
docker compose up -d      # PostgreSQL على 5432
npm install
cp .env.example .env
npm run db:push           # إنشاء الجداول
npm run db:seed           # بيانات تجريبية
npm run dev               # http://localhost:3000
```

### الإنتاج

- **الاستضافة:** Vercel (الأبسط) أو حاوية Docker على أي مزوّد.
- **قاعدة البيانات:** PostgreSQL مُدار (Neon / Supabase / RDS) مع نسخ احتياطي يومي.
- **الصور:** S3-compatible + CDN.
- **الترحيلات:** `prisma migrate deploy` في خط النشر — لا `db:push` في الإنتاج.
- **المراقبة:** تتبّع الأخطاء + تنبيه على فشل الدفع وWebhooks.
