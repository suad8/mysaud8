# فنجان — متجر قهوة مختصة وماتشا + لوحة تحكم

متجر إلكتروني سعودي (عربي/RTL) مبني بـ Next.js 15 + TypeScript + Tailwind CSS v4 + Prisma + PostgreSQL، مع لوحة تحكم إدارية كاملة الهيكل.

📄 الخطة الكاملة (البنية التحتية، نموذج البيانات، التكاملات، مراحل التنفيذ): [`docs/PLAN.md`](docs/PLAN.md)

## الحالة الحالية

- ✅ البنية التحتية: مشروع Next.js كامل، مخطط قاعدة بيانات شامل (18 نموذج)، بيانات تجريبية واقعية
- ✅ التصميم: واجهة متجر كاملة (رئيسية، تصنيف، منتج، سلة، دفع) + لوحة تحكم (رئيسية، منتجات، طلبات، عملاء، مخزون، خصومات، تقارير، إعدادات)
- ✅ **الدفع بالتحويل البنكي (حقيقي وفعّال):** العميل يختار «تحويل بنكي» في الدفع، يرى رقم الحساب من إعدادات المتجر، يؤكد ويرفق إيصالاً — فيُنشأ طلب حقيقي في قاعدة البيانات. الإدارة تراجع الإيصال من صفحة الطلب وتضغط تأكيد/رفض. **الدفع عند الاستلام** مفعّل أيضاً بنفس المسار.
- ⏳ بوابة Moyasar (مدى/بطاقات/Apple Pay): الإعدادات وتخزين المفاتيح جاهزة في لوحة التحكم، لكن الشحن الفعلي عبر API يحتاج حساب Moyasar حقيقي لاختباره.

المراحل التالية (مصادقة، سلة مرتبطة بجلسة حقيقية، CRUD فعلي كامل، شحن بوابات أخرى) موصوفة في `docs/PLAN.md`.

## التشغيل محلياً

```bash
# 1. قاعدة البيانات (عبر Docker، أو PostgreSQL محلي)
docker compose up -d

# 2. الاعتماديات
npm install

# 3. متغيرات البيئة
cp .env.example .env
# عدّل DATABASE_URL إذا لزم، ووَلِّد SESSION_SECRET بـ: openssl rand -base64 32

# 4. قاعدة البيانات (+ حساب مالك محلي — لا توجد كلمة مرور افتراضية في الكود)
npm run db:push
OWNER_EMAIL=you@example.com OWNER_PASSWORD='كلمة-مرور-قوية-12+' npm run db:seed

# 5. التشغيل
npm run dev
```

- المتجر: http://localhost:3000
- لوحة التحكم: http://localhost:3000/admin

## الأوامر

| أمر | الوصف |
|---|---|
| `npm run dev` | تشغيل بيئة التطوير |
| `npm run build` | بناء الإنتاج |
| `npm run typecheck` | فحص الأنواع |
| `npm run db:studio` | واجهة Prisma لتصفح البيانات |
| `npm run db:seed` | إعادة تعبئة البيانات التجريبية (محلياً فقط — يرفض العمل على قاعدة غير محلية) |
| `npm run db:create-owner` | إنشاء/تصفير حساب المالك: `OWNER_EMAIL=… OWNER_PASSWORD='…' [RESET=1]` |
| `npm run db:backup` | نسخة احتياطية لقاعدة البيانات وملفات الرفع في `backups/` |
| `npm run db:restore -- <ملف.dump>` | استعادة نسخة إلى `RESTORE_DATABASE_URL` |

## النسخ الاحتياطي والاستعادة

1. **دوري تلقائي (الأساس):** في Railway فعّل Backups لخدمة Postgres ولـ Volume ملفات الرفع (`/app/public/uploads`).
2. **نسخة يدوية خارجية** من جهازك (يتطلب `pg_dump` بنسخة ≥ نسخة الخادم):
   ```bash
   DATABASE_URL='<DATABASE_PUBLIC_URL من خدمة Postgres>' npm run db:backup
   ```
   الملفات في `backups/` مستثناة من git وتحتوي بيانات عملاء — احفظها في مكان خاص مشفّر.
3. **الاستعادة المجرَّبة:** استعد أولاً إلى قاعدة مؤقتة فارغة وقارن الأعداد التي يطبعها الأمر مع الأصل:
   ```bash
   RESTORE_DATABASE_URL='<قاعدة مؤقتة>' npm run db:restore -- backups/db-XXXX.dump
   ```
   الاستعادة إلى قاعدة غير محلية تتطلب `CONFIRM_DESTRUCTIVE=yes` صراحةً. ملفات الرفع تُستعاد بفك
   `backups/uploads-XXXX.tar.gz` داخل `public/`.

السكربتات التي تحذف بيانات (`db:seed`, `db:fresh-start`, `db:clear-demo`) ترفض العمل على Railway أو أي قاعدة غير محلية ما لم يُمرَّر `CONFIRM_DESTRUCTIVE=yes`.

## تحديث قاعدة البيانات عند النشر

أمر التشغيل `npm start` يزامن مخطط قاعدة البيانات تلقائياً (`prisma db push`) قبل تشغيل الخادم، فلا حاجة
لتشغيل أي أمر يدوياً بعد إضافة حقول جديدة. إن كان التغيير سيحذف بيانات يتوقف `db push` ويفشل النشر،
ويبقى الإصدار السابق يعمل (فحص `/api/health`) — عندها يُراجع التغيير قبل تطبيقه يدوياً.

## وضع الصيانة

الإعدادات ← «وضع الصيانة» (للمالك): الزوار يرون صفحة «نعود قريباً» برمز 503 (لا تضر ظهورك في قوقل)
ولا يمكن إنشاء طلبات، بينما يتصفح المدير المسجّل دخوله المتجر كالمعتاد لتجهيزه.

## صور ووصف المنتجات بالذكاء الاصطناعي (Gemini)

في صفحة المنتج بلوحة التحكم:
- «✨ اكتب الوصف بالذكاء الاصطناعي» — الوصف المختصر والكامل من اسم المنتج وتصنيفه وخياراته وملاحظاتك،
  بأسلوب احترافي أو ودّي. المعاينة قابلة للتعديل، و«استخدام» يضعها في الحقول وتُحفظ مع زر الحفظ.
- «✨ توليد صورة بالذكاء الاصطناعي» — صورة منتج احترافية، أو موك أب في مكان الاستخدام، أو موك أب
  يطبع شعارك/تصميمك على المنتج. المعاينة تظهر أولاً، و«استخدام هذه الصورة» يجعلها الصورة الرئيسية عند الحفظ.

1. أنشئ مفتاحاً من https://aistudio.google.com/apikey (توليد الصور عبر الـAPI قد يتطلب تفعيل الفوترة).
2. في Railway ← الخدمة ← Variables: أضف `GEMINI_API_KEY` بقيمة المفتاح (لا تضعه في الكود أو المحادثات).
3. اختياري: `GEMINI_IMAGE_MODEL` و`GEMINI_TEXT_MODEL` لتغيير نموذجي الصور والنصوص.

الصور تُحفظ في `public/uploads/products` — يلزم Volume دائم على `/app/public/uploads` حتى لا تضيع مع النشر.
حد التوليد 30 صورة و60 وصفاً في الساعة لكل مدير (للتحكم في التكلفة).
